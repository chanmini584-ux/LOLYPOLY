# Lolypoly 학교 PC 1대 운영·QR/PWA 시범 배포 — Claude Code 실행 프롬프트

작성 기준: 2026-11-04, 한국 시간.
사용법: 운영에 사용할 학교 PC의 Lolypoly 프로젝트 폴더에서 Claude Code를 열고 이 문서 전체를 전달한다.
다른 PC에서 실행했다면 그 사실을 밝히고, 학교 PC에 실제 적용한 것으로 보고하지 않는다.

너는 Lolypoly의 개발·서버 운영 담당자다. 아래 지시를 실행 계획으로만 끝내지 말고, 접근 가능한 환경에서 코드·서버 설정·실행·검증·운영 문서까지 완성해라. 이미 구현된 것은 재사용하고 필요한 수정만 한다.

## 1. 이번에 정한 목표

- Lolypoly는 한국폴리텍대학 춘천캠퍼스 학생을 위한 생활정보 서비스다.
- 작업 허브: https://github.com/chanmini584-ux/LOLYPOLY
- 기존 배포 주소(사용자 제공, 실제 상태 재확인): https://lolypoly-x7a3.onrender.com/
- 학교 공식 공개정보 출처: https://www.kopo.ac.kr/chuncheon/index.do
- 기획서 참고: https://claude.ai/artifact/2fnfEWXF8eoxugYpKRkUfD#7468d13a-ad43.mbxjtpstst1.2365
- 사용자 보고 기준으로 프로토타입·기획서는 교수님 검토를 받았다. 학교 공식 앱 지정이나 학교망 공개 허가까지 받은 것으로 간주하지 않는다.
- 이번 적용 대상은 **학교 PC 한 대**다. 그 PC에서 Django 웹앱과 정보 수집기를 실행한다.
- **Supabase 활용**, 서비스 도메인은 **lolypoly.com**, 배포 방식은 **QR로 접속하는 PWA**다.
- 도메인의 구매·소유·DNS 연결, Supabase 프로젝트 생성·연결이 완료됐다고 가정하지 않는다.
- 최우선 목표는 학생 20~30명에게 시범 사용하게 하고, 사용 경험을 모아 개선한 뒤 교수님께 결과와 다음 단계를 확인받는 것이다.
- 약 300명은 장기 잠재 이용자다. 300명이 동시에 접속한다고 가정한 대규모 인프라나 시험을 이번 필수 범위에 넣지 않는다.
- 학생은 학교 Wi-Fi·VPN 없이 집·LTE·5G에서도 https://lolypoly.com 으로 사용할 수 있어야 한다.
- 식단·학사일정·공지는 로그인 없이 열람한다.
- 기존 선택인 플래너 디자인과 최근 확정된 회원 기능 계획을 보존한다. 스토어 앱·새 프레임워크로 전환하지 않는다.

이번 작업의 완료 의미는 “학교 PC에서 서비스를 실행하고, 외부 HTTPS 접속과 핵심 데이터 보존·PWA를 확인한 뒤, QR 시범 운영과 피드백 수집을 시작할 준비가 됨”이다.
실제 학생 20~30명의 사용·피드백·교수님 확인은 시간이 필요한 후속 단계이며, 준비만으로 완료했다고 쓰지 않는다.

## 2. 목표 구조와 유지 원칙

역할을 아래처럼 나눠 구성한다.

| 역할 | 사용할 곳 | 주의할 점 |
|---|---|---|
| Django 웹앱 실행 | 학교 PC의 Linux 실행 환경 | 운영용 프로세스로 자동 실행 |
| Playwright 수집기 | 같은 학교 PC, 별도 예약 실행 | 학생 요청마다 실행하지 않음 |
| 회원·프로필·학생 의견 등 영구 데이터 | Supabase PostgreSQL 활용 | 기존 인증 방식·DB 결정 확인 |
| 공개 식단·일정·공지 | 기존 저장 구조 우선 유지 | SQLite라면 영구 경로·백업·동시 작업 검증 |
| 공개 주소 | https://lolypoly.com | 학교가 허용한 경로·HTTPS로 연결 |
| 학생 이용 | 브라우저 + 홈 화면 설치 PWA | QR을 찍는 것과 설치는 별도 |
| 코드·진행 기록 | 기존 GitHub 저장소 | 비밀값·학생 데이터 제외 |

Supabase는 Django 프로그램의 실행 장소를 대신하지 않는다. 학교 PC가 앱과 수집기를 맡고 Supabase는 데이터 역할을 맡는다.
현재 저장소의 D-038 같은 회원 PostgreSQL/공개정보 SQLite 분리 결정을 확인해 계승한다. 공개 DB까지 Supabase에 일괄 통합하는 것은 별도 핵심 변경이므로 임의로 진행하지 않는다.
Supabase Auth로 인증을 바꾸는 것과 Django 사용자 테이블을 Supabase DB에 저장하는 것은 다르다. 이미 선택한 인증 구조를 먼저 확인하고 유지한다.

기존 Docker 이미지가 빌드 시 수집한 DB를 담는 방식이면, 학교 PC에서는 정보 갱신과 코드 배포를 분리하고 사용자 기록을 재배포해도 유지되게 한다.
기존 Render는 새 서버의 검증이 끝나기 전까지 임의로 삭제·중단하지 않는다. 학교 PC 구성이 막혀도 Render로 자동 전환하거나 유료 클라우드를 새로 결제하지 않는다.

## 2-1. 현재 상태 보존 — 모든 작업의 최우선 조건

**현재 코드·화면·기능·DB 데이터·설정·기존 배포 상태를 보존한 채로 작업한다.**
이번 작업은 현재 프로젝트에 운영 기능을 덧붙이는 작업이다. 기존 프로젝트를 새로 만들거나 초기화하지 않는다.

- 시작 전에 브랜치·커밋·미커밋 변경, 실제 동작 기능, 기존 화면, DB·환경 설정·배포 구성을 확인해 기준 상태를 기록한다.
- 코드와 데이터에 복구 지점을 만든다. 커밋이 허용돼 있으면 작업 브랜치와 커밋을 활용하고, 허용되지 않았다면 기존 변경을 보존하는 별도 작업 공간과 안전한 백업을 사용한다. 사용자 변경을 임의로 버리거나 숨기지 않는다.
- 기존 .env·DB·설정의 백업은 접근을 제한한 위치에 보관한다. 비밀값이나 학생 데이터를 Git·공개 산출물에 넣지 않는다.
- 기존 UI·플래너 디자인·정상 기능을 유지한다. 서버 운영에 필요한 수정만 우선하고, 관련 없는 리팩터링·디자인 교체·의존성 일괄 업그레이드를 하지 않는다.
- 마이그레이션·설정 변경 전후에 데이터 보존을 검증한다. 기존 DB·테이블·마이그레이션을 삭제해 오류를 해결하지 않는다. 데이터 손실이나 되돌릴 수 없는 변환이 필요한 경우 안전한 대안과 복구 준비를 먼저 완성하고 그 변경만 확인을 요청한다.
- 새 학교 서버의 검증이 끝나기 전에 기존 Render 배포를 중단하거나 도메인을 전환하지 않는다. 전환할 때는 기존 주소·설정과 되돌리기 방법을 기록한다.
- 기존 상태를 바꿔야 하는 작업은 무엇이 왜 바뀌는지, 영향을 받는 기능과 복구 방법을 먼저 정리한다. 새로운 손실·비가역적 변경이 없는 범위는 자율 진행한다.
- 단계 완료 시 새 기능뿐 아니라 기존 핵심 화면·사용 흐름의 회귀 검증을 수행한다. 문제가 생기면 현재 변경을 수정하거나 해당 변경만 되돌릴 수 있게 한다.
- 최종 보고에서 유지한 내용, 변경한 내용, 복구 지점·백업 위치, 기존 기능 검증 결과를 구분한다. 백업 위치는 알려주되 비밀값은 노출하지 않는다.

완료 기준: 기존 기능·데이터를 유지했고, 이번 변경의 범위와 원래 상태로 돌아갈 방법을 확인할 수 있다.

## 3. 자율 진행과 작업 경계

- 이번 요청은 아래 단계의 연속 구현·설정·시험을 승인한다. 단계마다 “다음으로 진행할까요?”를 반복하지 말고 검증 후 계속 진행한다. 저장소의 과거 단계별 승인 대기는 이번 작업에 한해 이 지시로 대체한다.
- 기존 파일 수·변경량 제한이 있으면 작은 작업 단위로 나눠 지킨다.
- 미커밋 작업·기존 .env·DB·마이그레이션을 보존한다. 강제 초기화·일괄 덮어쓰기·DB 삭제를 하지 않는다.
- 커밋·푸시는 기존 사용자 정책을 따른다. 별도 승인이 필요한 정책이 있으면 로컬 변경과 검토 자료를 완성한 뒤 해당 행위만 남긴다.
- 사용자가 관리 권한을 제공한 학교 PC에 필요한 가역적 앱 설치·서비스 등록·배포·시험과, 관리 권한이 확인된 기존 도메인 연결은 이번 목표에 포함된다. 범위 안의 작업에 매번 다시 승인을 요구하지 않는다.
- 학교 PC를 관리할 권한과 학교망 외부 공개 허용 여부는 확인한다. 학교 담당자가 해야 하는 네트워크 변경을 대신 승인하거나, 제한을 우회하지 않는다.
- OS 재설치·포맷·파티션 삭제·기존 서비스 파괴·새 비용 발생·도메인 구매·학생에게 메시지 발송·교수님께 제출은 별도 지시 없이 실행하지 않는다.
- 비밀값은 안전한 로컬 설정·기존 승인된 비밀 저장소에서 다룬다. 비밀번호·토큰·학생 개인정보를 대화·Git·명령 출력·보고서에 노출하지 않는다.
- 필수 정보는 저장소·현재 PC·기존 설정에서 먼저 확인한다. 없으면 필요한 것만 한 번에 묶어 질문하고, 그 답 없이 가능한 구현·문서·검증은 계속한다.
- 필요한 계정 로그인·DNS 권한·학교 담당자 설정·휴대폰 조작 때문에 막히면 해당 항목만 사용자 작업 필요로 남긴다.
- 오류나 검증 실패는 재현 → 원인 → 최소 수정 → 재검증으로 처리한다.
- 과거 기록의 성공 결과를 이번 PC에서 실행한 결과로 복사하지 않는다.

## 4. 단계별 작업

### 0단계: 실행 위치와 최신 프로젝트 확인

1. 현재 PC의 OS, 실제 호스트/WSL/VM/컨테이너 여부, 작업 폴더, Git 원격·브랜치·변경사항을 확인한다.
2. 원격 주소가 작업 허브와 다르면 원인을 확인한다. 무조건 원격 교체나 git pull부터 실행하지 않는다.
3. 적용 지침, README, PROGRESS, PROJECT_BRIEF, DECISIONS, requirements와 관련 실제 코드를 읽는다.
4. 코드와 화면을 기준으로 식단·일정·공지·PWA·회원·피드백의 실제 구현/예시/미구현을 구분한다.
5. 최신 플래너·회원 기능 변경을 보존한다. 오래된 “회원 기능 범위 밖” 문구와 최근 확정 결정이 충돌하면 최신 사용자 지시와 확정 기록을 반영한다.
6. 기존 배포 주소와 도메인 연결 상태를 가벼운 요청으로 확인한다. 외부 기획서가 열리지 않으면 미열람으로 남기고 진행한다.
7. 기존 검사·테스트로 수정 전 기준을 남긴다.

완료 기준: 실행 대상, 변경 전 상태, 실제 구현, 남은 필수 조건을 설명할 수 있다.

### 1단계: 학교 PC 진단과 Linux 실행 환경 준비

- CPU·RAM·SSD 여유 공간·유선망·현재 서비스·관리 권한·절전·상시 전원 조건을 확인한다.
- 밤·주말·방학의 전원과 인터넷 유지가 가능한지 확인한다. 알 수 없는 조건은 미확인으로 적는다.
- Ubuntu LTS가 이미 설치돼 있으면 재사용한다. 실제 Python·의존성과 공식 지원 정보를 확인하고 불필요한 대규모 업그레이드는 피한다.
- Windows라면 먼저 기존 Linux VM/WSL 등 사용 가능한 환경을 조사한다. 이 환경을 쓴다면 Windows 부팅 후 자동 시작, 로그인하지 않은 상태의 앱 실행, 예약 작업과 외부 연결 유지까지 검증해야 한다.
- 새 Linux 설치가 필요하면 기존 데이터 백업과 구체적인 설치안을 준비하고 그 작업만 확인을 요청한다. OS를 임의로 지우지 않는다.
- 기본 Linux 운영 구성은 기존 Django + 가상환경 + Gunicorn + Nginx + systemd다. 이미 동작하는 동일 역할의 컨테이너 구성이 있으면 확인 후 재사용하고 중복 운영 체계를 만들지 않는다.
- 서버 전용 비관리자 실행 사용자, 시간 동기화, Asia/Seoul 기준 날짜·예약 작업을 준비한다.
- 원격 관리는 허용된 방법과 키 기반 접근을 우선한다. 접근을 잃을 수 있는 방화벽·SSH 변경은 기존 접속을 유지하며 검증한다.

완료 기준: 사용할 Linux 환경과 실측 사양이 확인되고, 설치 가능한 기반이 준비돼 있다. 실제 OS 설치가 남으면 준비/미설치를 구분한다.

### 2단계: 앱 실행·영구 저장·Supabase 연결

- 기존 설치 도구를 읽고 안전하게 가상환경·고정 의존성·Playwright 브라우저를 준비한다. 이미 있는 .env·DB를 덮어쓰지 않는다.
- 코드, 영구 데이터, 로그, 백업을 구분한다. 경로는 실제 환경에서 정하고 설치 스크립트의 설정값으로 받는다.
- 운영 설정(DEBUG=False, 비밀키, 허용 호스트, CSRF, HTTPS 프록시 신뢰)을 실제 연결 방식에 맞게 설정한다.
- Gunicorn 서비스와 필요한 Nginx 설정을 작성·등록한다. 앱은 부팅 후 자동 실행되고 프로세스 실패 시 재시작되게 한다. runserver로 공개하지 않는다.
- Supabase 프로젝트의 기존 용도·지역·접속 방식·무료 한도·비활동 정지 조건을 공식 자료에서 확인한다.
- 기존 Django 인증 모델과 DB 라우터를 확인한다. 인증·세션·권한·관련 테이블은 실제 관계를 검토해 같은 DB에 올바르게 배치하고 DB 간 외래키를 만들지 않는다.
- Supabase 연결 비밀값은 환경 설정으로만 넣고 TLS·연결 수·연결 풀러의 호환성을 확인한다. 기존 학생 데이터가 있으면 마이그레이션 전 백업한다.
- 연결값·프로젝트 권한이 없으면 로컬/별도 테스트 DB로 가능한 검증을 완료하고 실제 연결만 대기로 둔다.
- 공개정보를 SQLite로 유지하면 이미지 밖 영구 경로를 쓰고 수집·조회·백업의 동시 실행을 확인한다.
- Supabase 장애 시 공개정보 화면이 불필요하게 실패하지 않도록 실제 DB 호출·세션 처리를 시험한다. 회원 기능 실패를 성공한 것처럼 감추지 않는다.
- 기존 회원 기능 계획은 유지한다. 시범 운영에 노출하는 가입·로그인·로그아웃·프로필·탈퇴는 실제로 작동하게 하고, 미준비 기능은 명확한 안내 또는 설정으로 분리한다.
- 약 30일 로그인 유지가 구현 범위에 있으면 안전한 세션 만료·로그아웃/탈퇴 시 폐기를 검증한다. 학번 입력을 재학 인증으로 간주하지 않는다.

완료 기준: 로컬 및 운영 설정에서 핵심 화면이 실행되고, 연결한 DB의 저장·조회와 재시작 후 데이터 유지가 확인된다. 연결 준비와 실제 Supabase 연결은 구분한다.

### 3단계: 학교 밖 HTTPS 접속과 lolypoly.com 연결

- 학교가 제공하거나 이미 허용한 외부 연결이 있으면 우선 사용한다.
- 직접 공개 방식이면 공인 주소·라우팅·방화벽·포트·HTTPS 인증서 조건을 확인한다. 고정 IP나 공유기 변경 권한이 있다고 추측하지 않는다.
- 직접 공개가 어렵고 학교에서 터널 사용을 허용했다면 Cloudflare Tunnel 등 기존에 승인된 수단을 검토한다. 터널은 연결 통로이며 Django는 계속 학교 PC에서 실행된다는 점을 문서화한다.
- 터널을 고정 공개 주소에 연결할 때 필요한 도메인/DNS 권한·요금·학교망 연결 조건을 확인한다. 임시 무작위 주소를 인쇄용 최종 주소로 쓰지 않는다.
- 실제 소유·관리 권한이 확인된 lolypoly.com을 학교 서버에 연결한다. 현재 DNS를 기록·백업하고 메일 등 관련 없는 레코드를 보존한다.
- 이미 사용 중인 서비스가 있으면 준비된 새 서버를 검증한 뒤 연결을 전환한다. 실패 시 되돌릴 DNS·서버 절차를 남긴다.
- 대표 주소는 https://lolypoly.com 으로 일관되게 설정한다. www 사용 여부, 로그인 콜백, CSRF·호스트·PWA 경로가 충돌하지 않게 한다.
- 외부 관리 페이지나 DB 포트를 불필요하게 공개하지 않는다.
- 학교 안 브라우저 접속만으로 외부 접속 성공이라고 하지 않는다. LTE/5G 또는 다른 외부망에서 실제 확인한다.
- 외부 기기 조작·학교 허가·DNS 권한이 없으면 설정과 확인 순서를 완성하고 그 항목만 미확인으로 남긴다.

완료 기준: 학교 Wi-Fi·VPN 없이 외부망에서 유효한 HTTPS 주소로 핵심 화면이 열린다. 실제 외부망 검증 전에는 완료 처리하지 않는다.

### 4단계: 자동 수집·상태 확인·백업

- 화면 요청과 수집을 분리한다. 같은 PC의 별도 관리 명령과 systemd timer로 정보를 갱신한다.
- 기존 수집 주기를 확인하고, 시범 운영 초기값으로 식단·학사일정 하루 1회, 공지 하루 3회를 적용한다. 기존 잠정 주기와 달라지는 이유를 결정 기록에 남긴다.
- 종류별 실행 시간을 나누고 프로세스 중복 실행을 막는다. Playwright 브라우저가 여러 개 겹쳐 PC 메모리를 과도하게 쓰지 않게 한다.
- 서울 시간·실행 사용자·가상환경·브라우저·DB 경로를 맞춘다. 재부팅 후 놓친 예약 처리와 실패 재시도 상한을 설정한다.
- 수집 실패·구조 변화·빈 결과에서도 이전 정상 데이터와 마지막 성공 시각을 보존한다. 공식 원문 링크와 정보 지연 안내를 유지한다.
- 공식 사이트에는 기존 요청 간격을 지키고 소량으로 검증한다. 부하 시험으로 학교 홈페이지를 호출하지 않는다.
- 운영자에게 수집 성공/실패·앱 상태·로그를 확인할 방법을 제공한다. 로그에 비밀값과 개인 입력을 남기지 않고 크기를 제한한다.
- 초기 백업 목표는 하루 1회·최근 7일 보관으로 두되 기존 정책이 있으면 우선한다. Supabase 무료 요금제에 유료 자동 백업이 포함됐다고 가정하지 않는다.
- SQLite는 실행 중 정합성을 보장하는 백업 방법, Supabase PostgreSQL은 해당 연결·권한에 맞는 내보내기 방법을 사용한다.
- 별도 테스트 위치에서 복원해 데이터와 앱 동작을 확인한다. 같은 디스크 복사만을 외부 백업이라고 하지 않는다.
- 승인된 다른 장치의 백업 목적지가 있으면 연결하고, 없으면 외부 백업 미확보로 기록한다. 임의로 외부 계정에 학생 데이터를 업로드하지 않는다.

완료 기준: 수집 성공·실패·중복 방지, 타이머 등록, 서비스 재시작과 백업 복원을 확인했다. 실제 예약 시각 실행을 관찰하지 못했다면 별도 표시한다.

### 5단계: QR로 들어오는 PWA 사용 흐름 완성

- 학생은 QR을 찍어 웹을 바로 사용하고, 원하면 홈 화면에 추가한다. QR 스캔이 곧 자동 설치라고 안내하지 않는다.
- 375~430px에서 식단·일정·공지·의견 보내기와 주요 링크를 검증한다. 기존 플래너 디자인을 보존한다.
- HTTPS, 매니페스트, 아이콘, 서비스 워커 범위, 새 버전 갱신, 저장 화면/오프라인 안내를 확인한다.
- iPhone과 Android 설치 방법을 각각 짧게 안내한다. 실제 지원 기기·브라우저 동작을 확인하고 데스크톱 에뮬레이션과 구분한다.
- 개인정보가 포함된 응답·로그인·MY·개인 시간표·의견 내역·관리 화면은 서비스 워커·공유 캐시에 저장하지 않는다.
- 공개 경로에 로그인 이름 등 개인 내용이 섞이는지도 검사한다. 로그아웃·계정 변경·탈퇴 후 이전 개인 화면이 남지 않게 하고 기존 위험 캐시도 정리한다.
- https://lolypoly.com 을 담은 QR PNG 또는 SVG와 A4 게시용 안내물을 준비한다. 생성 후 실제 디코딩으로 주소를 검증하고 충분한 여백·대비를 유지한다.
- 도메인이 아직 연결되지 않았으면 QR 결과물은 인쇄 전 검증 대기로 표시한다. 게시 가능하다고 보고하지 않는다.
- 안내물에는 서비스명, 식단·일정·공지의 용도, 시범 서비스라는 사실, 홈 화면 설치와 의견 보내는 방법을 간결하게 넣는다.
- 학생 의견이나 전화번호·비밀 URL을 공개 게시물에 노출하지 않는다. 실제 게시와 학생 연락은 사용자가 진행한다.

완료 기준: 실제 HTTPS에서 핵심 흐름·설치·갱신을 점검하고 QR 주소가 정확하다. 실제 휴대폰이 없으면 실기기 검증만 미확인으로 남긴다.

### 6단계: 20~30명의 사용 경험을 모을 준비

- 시범 운영의 목표는 가입 숫자만 늘리는 것이 아니라 20~30명의 실제 사용 경험을 확보하는 것이다. 20~30명을 앱의 고정 이용 제한으로 구현하지 않는다.
- 기존 피드백 기능이 있으면 활용한다. 없으면 앱 안에 짧은 의견 폼과 운영자 확인 기능을 만들고 Supabase의 영구 저장 구조와 연결한다.
- 질문은 “유용했던 기능 / 막히거나 불편했던 점 / 다시 사용할 이유 또는 원하는 개선”을 중심으로 간단히 구성한다.
- 이름·학번·전화번호·첨부파일은 기본 수집하지 않는다. 공개 핵심 정보와 의견 제출을 위해 불필요한 회원가입을 강요하지 않는다.
- 입력 길이·형식, CSRF, 출력 이스케이프, 도배 제한, 관리자 권한을 검증한다.
- 필요한 이용 통계는 기능별 집계·오류·수집 상태부터 시작한다. 방문 횟수를 사람 수로 간주하지 않는다.
- 반복 응답을 분리할 필요가 있으면 개인정보를 최소화한 임시 참여 코드 등 간단한 방법을 제안하고 기존 합의가 있으면 활용한다. 피드백 20건만으로 서로 다른 20명이라고 단정하지 않는다.
- 실제 수집 항목·목적·보관 기간을 안내한다. 기존 기준이 없으면 개별 의견 30일을 초기 운영안으로 제시하고 적용 전에 확인할 항목으로 남긴다. 기존 데이터에 임의의 일괄 삭제 정책을 실행하지 않는다.
- 측정할 과업은 “오늘 점심 확인 / 내 과정의 일정 확인 / 공지 원문 열기 / 의견 보내기”처럼 구체적으로 잡는다.
- 학교 홈페이지와 비교할 때 같은 과업을 사용한다. 실제 측정 전에는 시간 절감·만족도·재방문 수치를 만들지 않는다.

완료 기준: 의견 등록·관리자 조회·재시작 후 보존이 확인되고, 학생에게 줄 짧은 체험 과업과 피드백 안내가 준비됐다.

### 7단계: 운영 시험·보고·인계

- 프로젝트의 실제 명령을 확인한 뒤 Django 검사, 마이그레이션 누락 검사, 기존 테스트와 필요한 회귀 테스트를 실행한다.
- 정상 흐름 외에 DB/수집 실패·개인 캐시·권한·데이터 보존·설정 누락 경로를 확인한다.
- 로컬/별도 테스트 환경에서 우선 5~10명 수준, 이어 30명 수준의 현실적인 읽기 요청을 시험한다. 300명 동시 접속 시험은 이번 필수가 아니다.
- 주요 화면 p95 2초 이내·서버 오류율 1% 미만을 초기 관찰 목표로 두되 실측 결과로 판단한다. 장치 사양·요청 비율·대기 시간·CPU/메모리·수집 동시 실행 영향을 기록한다.
- 학생 통계에서 테스트 트래픽을 분리한다. 외부 홈페이지에는 부하를 보내지 않는다.
- 앱 재시작·학교 PC 재부팅 후 자동 실행·외부 재접속·수집·데이터 유지·백업 복원을 확인한다. 재부팅은 작업 저장과 원격 접근 복구 방법을 확보한 뒤 진행한다.
- 교수님께 보여줄 한 페이지 결과 양식을 준비한다: 실제 참여 인원, 유용했던 기능, 주요 불편, 개선 전후, 서버 운영 상태, 남은 문제, 다음 배포 제안.
- 실사용 전 양식은 빈칸/수집 대기로 남긴다. 실제 교수님 확인·학교 공식 승인을 받은 것으로 쓰지 않는다.
- 담당자가 이어받을 수 있도록 시작/중지/상태 확인, 업데이트, 수집, 백업·복원, 장애 대응, 도메인·계정 소유자 확인 방법을 문서화한다.
- 보유 계정·도메인의 실제 비용과 무료 한도를 정리하고, 학교 PC 전원·망·관리 책임 중 미확인 항목을 적는다.

완료 기준: 실행한 시험 근거, 시범 배포 준비 상태, 사용자 작업, 운영 인계 방법을 구분해 전달할 수 있다.

## 5. 산출물과 보고 방식

기존 문서를 우선 갱신하고 중복 문서는 줄여라. 필요한 새 경로는 저장소를 확인한 뒤 정한다.

필수 산출물:
1. 현재 상태·결정 기록과 최신 실행 방법.
2. 실제 설치·업데이트·자동 실행·예약 수집·로그·백업·복원 설정/스크립트.
3. Supabase 연결 설정 예시와 DB별 저장 위치 표. 비밀값은 제외한다.
4. lolypoly.com 연결·HTTPS·외부 접속 점검 기록 및 되돌리기 절차.
5. QR 이미지, 게시용 안내물, iPhone/Android PWA 설치 안내.
6. 최소 피드백 기능·수집 안내·시범 체험 과업.
7. 테스트 결과·실기기 점검표·교수님 결과 보고 양식·다음 작업 기록.

버전별 설정은 실제 설치 버전과 공식 자료로 확인하고 근거 링크와 날짜를 남긴다. 특정 버전을 “최신”이라고 추측하지 않는다.

사용자 보고는 한국어 반말로, 첫 줄은 “내가 받아들인 내용은:”으로 시작한다.
단계 전환마다 지금 완료된 것·남은 것·다음 행동을 짧게 알려주고, 검증 후 다음 작업을 계속한다.
설명은 7살도 이해할 수 있게 하되 정확한 기술 정보와 실행 명령은 문서에 남긴다.

최종 보고는 아래 순서로 간결하게 한다.
- 결론: QR 시범 배포 가능 / 조건부 / 아직 불가, 근거.
- 실제로 바뀐 것과 검토할 파일.
- 코드 작성 / 로컬 시험 / 학교 PC 등록 / 외부 HTTPS / 실기기 검증 / QR 게시를 구분한 상태표.
- 실행한 검사·테스트·운영 시험 결과와 미실행 항목.
- 추가 비용 발생 여부, 커밋·푸시·실제 배포 여부.
- 찬민이 직접 해야 하는 일 최대 5개: 대상·정확한 행동·완료 기준.
- 20~30명 시범 운영 시작 방법과 교수님 확인까지의 다음 단계.

시간·연결·대화 제한이 오면 마지막 완료 단계, 변경 내역, 실행한 검증, 차단 요인, 바로 다음 명령을 기존 진행 문서에 남긴다.
없는 권한·실제 휴대폰·학교 담당자 조치 때문에 못 한 항목만 정확히 남기고, 가능한 작업은 모두 끝내라.

지금 0단계부터 시작해라.

설치·검증·운영 문서까지 자율 진행하고, 실제 학생 반응을 바탕으로 개선 후 교수님께 확인받는다.
